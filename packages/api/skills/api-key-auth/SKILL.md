# API Key Auth

Bearer API key authentication for the FIBA OCR API. Every request to `/v1/runs/*` must carry a valid key. There are three layers (see `packages/api/AGENTS.md` § Auth is layered); this skill covers the **API key layer** — the one that fires for any Bearer token starting with `ocr_`.

## When to use

- Adding a new route under `/v1/runs/*` (the middleware already handles auth).
- Debugging a 401 from the API.
- Generating a key for a new caller (MCP, web, external).
- Understanding the key lifecycle (`api_keys` table, `bootstrap`, `DELETE`).

## Key format

```text
ocr_live_<64 hex chars>
```

- Always prefixed with `ocr_live_`.
- Followed by 64 hex characters (`secrets.token_hex(32)` — 32 random bytes).
- Example: `ocr_live_a1b2c3d4e5f6...` (64 chars after the prefix).
- Generated by `ocr_engine_api.api_keys.generate_api_key`.
- Hashed with SHA-256 by `ocr_engine_api.api_keys.hash_api_key` before being written to the `api_keys` table.

The raw key is returned to the user **exactly once** (typically from `POST /v1/me/api-keys/bootstrap`). It is never stored, never logged, and never returned by `GET /v1/me/api-keys`.

## How validation works

The `api_key_auth` middleware in `ocr_engine_api.auth_api_key`:

1. Skips for `OPTIONS` requests and exempt URLs (`/health`, `/v1/me/*`).
2. If the Bearer token starts with `ocr_`, treats it as an API key request and calls `validate_api_key`.
3. `validate_api_key`:
   - SHA-256 hashes the raw key.
   - Looks up the hash in the 60-second in-memory cache. Cache hit → proceed.
   - Cache miss → queries the `api_keys` table via Supabase (or the configured backend) for an active key matching the hash.
   - Cache miss + DB hit → stores the result in the cache for 60s, fires a fire-and-forget `update_last_used_at`, proceeds.
   - Cache miss + DB miss → returns a 401 with the standard error envelope (`error.code = "UNAUTHORIZED"`).
4. If the Bearer token does not start with `ocr_`, falls back to the static-bearer check (`auth.is_authorized(settings.api_key)`). This is the dev fallback.

## What "active" means

A key row in the `api_keys` table is considered active when its `status` column is `active`. The `/v1/me` lifecycle is:

- `POST /v1/me/api-keys/bootstrap` — generates the first key for the account and returns the raw key once. If an active key already exists, responds `409 API_KEY_ALREADY_EXISTS` (it does not delete the existing key).
- `POST /v1/me/api-keys` — creates an additional named key.
- `GET /v1/me/api-keys` — lists keys (without the secret).
- `DELETE /v1/me/api-keys/{key_id}` — hard-deletes the key row. We **do not** mark keys as revoked; deletion is permanent.

## Adding a new caller

1. Generate a key (via the dashboard or `POST /v1/me/api-keys`).
2. Send it on every request: `Authorization: Bearer ocr_live_<32 hex>`.
3. For HTTP clients, prefer the helpers in `packages/web/src/lib/api.ts` (web) or the `OcrApiClient` (MCP).
4. For long-running callers, keep the key out of logs and config files. Use the environment variable `OCR_API_KEY` (MCP) or pass it through a secret manager.

## Debugging a 401

- The key is well-formed (`ocr_live_<32 hex>`)? If not, the middleware falls back to the static bearer — and likely returns 401.
- The key row is `active` in the `api_keys` table? If it's been deleted, it's gone forever; the user must bootstrap a new one.
- Is the API configured with `OCR_ENGINE_API_KEY` and the same key? For production mode, both sides must agree.
- The Bearer header is correctly formed: `Authorization: Bearer <key>` (single space, no extra quotes)?

## Constraints (do not violate)

- Do not weaken `api_key_auth` to skip the Bearer check, even in development. Use the static-bearer fallback instead.
- Do not log the raw key, store it in a config file, or include it in a stack trace.
- Do not return the raw key from `GET /v1/me/api-keys` or any other read endpoint. Once-only.
- Do not store the raw key in the `api_keys` table. Only the SHA-256 hash.
- Do not extend the 60s cache TTL beyond what is operationally necessary. Keys must be revocable within ~1 minute.
